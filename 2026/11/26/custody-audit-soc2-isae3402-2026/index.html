托管审计报告怎么读：SOC 1、SOC 2、ISAE 3402 与 Type I/II 的区别

Bitbank2026-11-262026-11-26

币安|Binance
欧意|OKX

导读：托管方说「我们通过了 SOC 2」，正确的追问是三个：Type 几、审计期间多长、签名服务在不在范围内。答不出后两个，这份报告几乎不能用于决策。

四份报告，四个问题

加密托管方常把几份报告混着说，但它们回答的是完全不同的问题：

报告 回答的问题 谁需要
SOC 1 Type II 与客户财务报表相关的控制是否有效运行 基金的年度审计师
SOC 2 Type I 某一天，控制设计是否合理 初步筛选
SOC 2 Type II 一段期间内，控制是否实际运行 机构准入的实质门槛
ISAE 3402 SOC 1 的国际对应版本 非美辖区的审计师

关键差别在 Type I 与 Type II。Type I 是快照：它告诉你「审批流程、权限管理、变更管理在设计上是对的」。Type II 是录像：它附带审计师对每项控制的测试程序与结果，覆盖通常 6 至 12 个月。只有 Type II 能回答「这些控制是不是每天真的在执行」。

拿到一份报告，翻到目录就能判断：有「控制测试及结果」章节的是 Type II，没有的是 Type I。如果对方只能提供 Type I，正确的追问是「Type II 的时间表」。

SOC 2 的五类准则，以及管理层挑了哪几类

SOC 2 依据美国注册会计师协会（AICPA）的信任服务准则，覆盖五类：安全性、可用性、处理完整性、机密性、隐私性。报告可以只覆盖其中一类或几类，由管理层在界定范围时选择。

对托管方，最常见的是「安全性 + 可用性」，机密性与隐私性视业务而定。这不是瑕疵，但意味着：如果一份报告只覆盖安全性，它不评价你的资产记录是否准确（处理完整性），也不评价隐私数据处理。

2026 年 10 月，AICPA 的相关委员会发布了 2027 年准则的征求意见稿。这属于提案阶段，现行有效的仍是 2017 年准则（含 2022 年修订的关注点）。

报告边界：管理层写的那段「系统描述」

这是最容易被跳过、却最关键的部分。SOC 2 的结构是：

  1. 管理层撰写的系统描述（范围、系统边界、控制措施）；
  2. 管理层声明；
  3. 审计师意见；
  4. （Type II）控制测试及结果。

审计师只对「描述里写了的东西」发表意见。 描述之外的系统，报告不覆盖。

由此衍生两个技术细节：

  • 分包服务机构（carve-out 与 inclusive）。 若托管方依赖云厂商或 KMS 服务商，报告可以把这些控制纳入（inclusive），也可以排除在外（carve-out）。采用后者时，你必须另行获取分包方的报告，否则中间有一段是空白的。
  • 补充用户实体控制（CUECs）。 报告会列出「需要客户自己执行」的控制——比如你自己的账号权限设置、审批人配置、设备管理。托管方的控制只有在这些到位时才成立。这一节常被忽略，但它是责任划分的正式依据。

三种「看了但没覆盖」的风险

即使报告范围完整、期间足够近，SOC 2 仍有三类结构性盲区，因为它们审计的是控制，不是结果。

第一，智能合约逻辑。 报告能看见「代码部署是否有变更审批」，看不见「部署的代码是否正确」。这两件事完全不同。2026 年 3 月的一起事故是这个组合的教科书案例：攻击者先进入云环境中的特权签名密钥，随后合约本身没有设置增发上限，两段拼起来才构成完整损失。前者是访问控制问题，后者是代码逻辑问题——而后者不在 SOC 2 的射程内。

第二，密钥与签名界面。 报告能看见「谁有权签名、权限如何回收」，看不见「签名人是否真的能读懂他在签什么」。盲签问题在托管场景里尤其致命：一个控制完美的流程，可以稳定地批准一笔恶意交易。

第三，链上监控的覆盖。 如果监控的合约、角色、多签地址没有写进系统描述，它们就不在报告范围内。

因此，一份可用的证据组合至少是四件套：SOC 2 Type II（控制）、智能合约审计（代码）、渗透测试（应用与签名服务）、密钥管理评审（流程与仪式）。任何一件单独拿出来，都不足以支撑「资产安全」这个结论。

三个易被混淆的「证明」

名称 证明什么 不证明什么
SOC 2 Type II 控制在一段期间内有效运行 资产是否 1:1 存在、代码是否正确
储备证明（PoR） 某一时点的资产 ≥ 负债（按特定口径） 负债是否完整、资产是否被重复计算
冷存储覆盖率 离线合格资产 ÷ 客户负债 资产可动用性、权利负担、同一攻击下的相关性

三者互补，不能互相替代。一家可以同时拥有漂亮的 SOC 2、100% 以上的冷存储覆盖率，以及一份只覆盖部分负债的储备证明。读的时候要问「分母是什么」，而不是「数字是多少」。

一份报告的六步阅读法

  1. 看类型：Type II，且期间结束日距今不超过 12 个月。
  2. 看范围：签名服务、密钥管理系统、管理控制台是否在系统描述里；钱包产品线是否全部覆盖。
  3. 看准则：覆盖了五类中的哪几类；处理完整性是否在范围内。
  4. 看例外：报告会列「例外事项」（exceptions）——即测试未通过的控制。一家诚实披露 3 条例外的托管方，通常比一家零例外的更可信，因为零例外往往意味着范围太窄。
  5. 看 carve-out：分包方是谁，你有没有拿到他们的报告。
  6. 看 CUECs：哪些控制要你自己做，你的团队是否真的在做。

第 4 条值得展开。例外事项不是「黑名单」，而是风险定位：它告诉你哪一环在压力下最可能失效。忽略它，等于只读了封面。

报告之外：三个不能替代的问题

  • 资产在哪？ 托管方是作为受托人持有，还是以自身名义持有？破产时的取回权取决于此。
  • 谁能单方面动？ 多签的阈值、参与方、以及是否有一方可以独自暂停或升级。
  • 保险覆盖什么？ 犯罪险通常不覆盖智能合约漏洞与客户凭证泄露，且总限额是保单期内的累计上限。

这三条都不在审计报告里，但它们的权重不低于报告本身。

在 币安 或 欧意 OKX 存放资产时，可对照的思路是：平台公布的储备证明解决「有没有」，审计报告解决「流程稳不稳」，而托管架构解决「出事后能不能拿回来」。三个问题对应三种证据，不要用一份材料去回答另一个问题。

结语

审计报告的价值不在于它有多厚，而在于它明确划出了一条边界：边界内是「被测试过的控制」，边界外是「未被评价的风险」。专业的使用方式，是把边界外的那部分单独补齐，而不是把报告当作一张通行证。

一家托管方愿意主动告诉你边界在哪、例外是什么、哪些控制要你自己做——这本身就是一项比报告更可靠的信息。

本文为尽调方法分析，不构成投资或法律建议。具体报告范围以正式文件为准。
