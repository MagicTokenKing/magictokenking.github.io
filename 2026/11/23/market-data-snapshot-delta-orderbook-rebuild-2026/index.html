订单簿是重建出来的：快照、增量与序列号

Bitbank2026-11-232026-11-23

币安|Binance
欧意|OKX

导读：策略的输入从来不是「价格」，而是一个被持续重建的数据结构。它的正确性没有兜底，只有校验。

三个流，缺一不可

交易所的行情接口通常由三部分组成：

  1. 快照（snapshot）：某一时刻的完整盘口，通过 REST 拉取，带一个序号。
  2. 增量（diff）：只推送发生变化的价格档位，通过 WebSocket 持续到达，每条的序号连续。
  3. 心跳（heartbeat / ping）：证明连接仍然活着，也用于发现静默断流。

单用增量无法启动（不知道初始状态），单用快照无法维持（拉一次就过期）。必须把两者缝合，而缝合点就是序号。

重建的六步

一个正确的重建流程大致如下：

  1. 先建立 WebSocket 连接，把增量缓冲在内存里，暂不应用。
  2. 拉取快照，记录其序号 S。
  3. 丢弃缓冲区中序号 ≤ S 的增量（它们已被快照包含）。
  4. 从第一条序号 > S 的增量开始，逐条应用。
  5. 每条应用后校验：序号是否连续？校验和是否匹配？
  6. 任何一步失败，清空本地盘口，回到第 1 步。

第 6 步是最容易被省略、也最致命的一步。很多系统在发现缺口后选择「跳过缺失的增量继续用」，这在平静市场里看不出问题，但在剧烈波动时会留下一个永远不会自愈的错误盘口——而策略会把它当成真实流动性。

量级：一天几十万次机会出错

假设订阅 20 档、单symbol 每秒 50 条增量、每天运行 8 小时：

50 × 3,600 × 8 = 144 万条增量

若单条增量的丢失概率是 10⁻⁶（对公网 WebSocket 来说并不保守），则日均有约 1.4 次缺口。也就是说，在没有任何代码 bug 的情况下，一个正常系统每天都会遇到一到两次必须重建的事件。重建逻辑不是异常分支，而是主路径的一部分。

序号的三种语义

不同交易所对「序号」的定义不同，混淆它们是常见 bug 来源：

语义 含义 陷阱
单条递增 每条增量一个全局序号 撮合引擎重启后可能归零
区间 每条增量携带 [首序号, 末序号] 需要判断「首序号 ≤ 本地末序号+1」才算连续
快照序号 + 版本 快照带版本号，增量带版本区间 版本回滚时需整体重置

第三种最容易被误判：当交易所做撮合引擎迁移时，版本号可能从高位回到低位，看起来像「倒退」，实际上是新引擎。此时正确的动作仍是清空重建，而不是取最大值继续。

校验和：唯一能发现「静默错误」的手段

序号能发现「丢了消息」，但发现不了「消息内容错了」或「本地计算错了」。校验和补上这一层。

常见做法是把前 N 档的「价格:数量」拼成字符串，做 CRC32 或类似校验，与推送中的字段比对。某主流交易所校验前 25 档，另一家对前 10 档做 CRC32。档位数不同意味着不能用同一套代码直接套用——档位取错，校验永远失败或永远通过，后者更危险。

校验失败率是一个极好的系统健康指标。正常情况下它应该接近零；如果持续出现，说明本地解析、精度处理或档位截取有问题，而不是网络问题。

精度：一个被低估的错误源

价格与数量在不同交易所使用不同小数位，且通常以字符串传输以避免浮点误差。用 float 解析 0.1 再加总，会得到 0.30000000000000004。这类误差在盘口层面看起来无害，但在两处会致命：

  • 校验和：字符串与浮点转换后的字符串不一致，校验必然失败。
  • 价格比较：0.1 + 0.2 > 0.3 为真，会导致本应成交的订单被判为不可成交。

正确做法是全程使用定点整数（按最小价格单位放大），只在展示层转回小数。

常见陷阱清单

  1. 快照比缓冲更旧。若快照序号小于缓冲中最早的增量序号，说明快照已过期，必须重拉。
  2. 同一毫秒内乱序。部分交易所的增量在同一时间戳内不保证顺序，只能依赖序号。
  3. 时间戳非单调。撮合与推送的时间戳来自不同时钟，不能用作排序依据。
  4. 心跳超时不等于断线。TCP 连接可能仍然存在但不再推送，需要业务层超时（如 3 秒无增量即重连）。
  5. 重连后的重复应用。重连时若不清空本地状态，会把旧增量重复叠加，形成幽灵档位。
  6. 多symbol 内存泄漏。1000 个 symbol × 20 档 × 双边，若每档存一个对象，内存与 GC 压力会显著影响延迟。

应该监控什么

一套行情系统至少要暴露四个指标：

指标 健康值 说明
缺口次数 / 小时 < 0.5 高于此值说明网络或解析有问题
重建耗时 p99 < 500 ms 决定断流期间策略的盲区长度
校验失败率 ≈ 0 持续非零即为代码问题
交叉盘口比例 ≈ 0 买一价 ≥ 卖一价，说明状态错乱
快照年龄 < 1 s 启动阶段的关键约束

其中「交叉盘口」是最灵敏的报警：真实市场几乎不会出现买价高于卖价（出现也会在毫秒内被套利抹平），一旦本地状态里稳定存在交叉，几乎必然是重建逻辑错了。

为什么这件事值得认真对待

错误的盘口会沿着系统向下传导：

  • 做市策略把「幽灵深度」当成可成交流动性，报出无法兑现的价差；
  • 风控用错误的中间价计算保证金，导致该强平的不平、不该平的被平；
  • 回测用重建错误的档口数据，得到一个在实盘中不存在的夏普比率；
  • 清算引擎按错误的深度估算滑点，低估了实际穿价幅度。

这些错误的共同点是：不报错、不崩溃、只是安静地给出错误答案。在 2026 年这个流动性明显变薄的市场环境里（主流现货价差经常在个位数基点、深度对单笔大额订单极其敏感），错误的深度估计比错误的价格更危险。

在 币安 或 欧意 OKX 查看盘口时，界面上那个平滑更新的深度图，背后就是这套逻辑。它的可靠性不取决于界面，而取决于服务端的重建代码有没有在每一次缺口时老老实实地清空重来。

结语

行情工程是量化交易里最没有成就感的部分：做对了，一切正常；做错了，也没有人立刻发现。它的验收标准不是「跑起来」，而是「在 144 万条增量里丢掉一条时，能在一秒内回到正确状态」。

把重建当成主路径而不是异常处理，把校验和当成必需而不是可选，把交叉盘口当成红线而不是噪声——这三件事做完，才算真正拥有了自己的盘口。

本文为交易系统数据工程讨论，不构成投资建议。各交易所接口细节以其官方文档为准。
